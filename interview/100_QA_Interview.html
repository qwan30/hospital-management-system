🏥 100 Câu Hỏi Phỏng Vấn: Hospital Management System

Tài liệu tổng hợp 100 câu hỏi trọng tâm nhất dựa trên kiến trúc Modular Monolith, DDD, Spring Boot 3.3, và Next.js 16 của dự án. Trả lời theo chuẩn phương pháp STAR.

S: Ngữ cảnh (Situation) T: Nhiệm vụ (Task) A: Hành động (Action) R: Kết quả (Result)

🏗️ Kiến trúc & Domain-Driven Design (DDD)

#1 Tại sao dự án chọn Modular Monolith thay vì Microservices? ▼
S
Các quy trình y tế có tính liên kết luồng chảy rất chặt chẽ (đặt lịch -> xếp hàng -> khám -> thanh toán).
T
Cần một hệ thống dễ triển khai, chi phí hạ tầng thấp nhưng vẫn đảm bảo tính module hóa để dễ mở rộng sau này.
A
Áp dụng Modular Monolith kết hợp Domain-Driven Design (DDD), chia thành 17 Bounded Contexts độc lập trong 1 codebase.
R
Loại bỏ hoàn toàn chi phí (overhead) của distributed transactions, hệ thống chạy mượt trên 1 server mà code không bị tight-coupling.
#2 Bạn định nghĩa Bounded Context trong dự án này như thế nào? ▼
S
Trong bệnh viện, thực thể 'Bệnh nhân' ở khâu Khám bệnh mang ý nghĩa khác hoàn toàn với 'Bệnh nhân' ở khâu Thanh toán.
T
Phải phân định ranh giới ngữ nghĩa rõ ràng để tránh mô hình dữ liệu bị phình to và rối rắm.
A
Tạo các Bounded Context riêng (Appointment, Patient, Billing), mỗi context có model riêng biệt không chia sẻ chung.
R
Code dễ bảo trì, team phát triển các module không dẫm chân lên nhau, sẵn sàng tách thành Microservice nếu cần.
#3 Dependency Inversion được áp dụng ra sao giữa Domain và Infrastructure? ▼
S
Logic nghiệp vụ (Domain) thường hay bị gắn chặt với công nghệ truy xuất dữ liệu (ví dụ: Spring Data JPA).
T
Cần làm cho Domain layer độc lập hoàn toàn khỏi Infrastructure để dễ test và thay đổi database.
A
Định nghĩa các Repository Interface ở Domain Layer, còn class implement thực tế nằm ở Infrastructure Layer.
R
Domain không biết gì về cơ sở dữ liệu. Có thể unit test nghiệp vụ y tế hoàn toàn độc lập không cần bật database.
#4 Aggregate Root trong hệ thống Đặt lịch khám là gì? ▼
S
Một cuộc hẹn khám bệnh đi kèm với rất nhiều dữ liệu phụ (lịch sử, triệu chứng, file đính kèm).
T
Cần một điểm vào (entry point) duy nhất để đảm bảo tính toàn vẹn dữ liệu khi có thay đổi.
A
Chọn `Appointment` làm Aggregate Root. Mọi thao tác đổi trạng thái, thêm triệu chứng đều phải gọi qua class `Appointment`.
R
Đảm bảo tính nhất quán dữ liệu (Consistency), không có logic nào cập nhật lén các bảng phụ bên ngoài Aggregate.
#5 Sự khác biệt giữa Entity và Value Object trong dự án? ▼
S
Trong nghiệp vụ y tế, có những đối tượng cần định danh duy nhất (Bệnh nhân) và những đối tượng chỉ mang giá trị (Địa chỉ, Nhóm máu).
T
Cần thiết kế model phản ánh đúng bản chất nghiệp vụ để code an toàn và dễ hiểu hơn.
A
Dùng Entity (có ID) cho Patient, Doctor. Dùng Value Object (không ID, Immutable) cho Address, Money, TimeSlot.
R
Giảm thiểu bug liên quan đến side-effects do Value Object là bất biến (immutable), an toàn trong môi trường đa luồng.
#6 Làm sao các Bounded Contexts giao tiếp với nhau? ▼
S
Module Billing cần biết khi module Appointment hoàn thành khám để tạo hóa đơn, nhưng không được gọi code trực tiếp của nhau.
T
Thiết lập cơ chế giao tiếp nội bộ lỏng lẻo (loose-coupling) giữa các module.
A
Sử dụng Spring ApplicationEventPublisher để phát event nội bộ, hoặc dùng Application Services Interface.
R
Các module không bị phụ thuộc vòng (circular dependency), dễ dàng mở rộng và thêm module mới (như Pharmacy) mà không sửa code cũ.
#7 Bạn xử lý Transaction vượt ranh giới module như thế nào? ▼
S
Khi bác sĩ chốt đơn thuốc, vừa phải lưu hồ sơ (EHR module) vừa trừ tồn kho (Pharmacy module).
T
Đảm bảo tính ACID nhưng không làm giảm hiệu năng hệ thống.
A
Sử dụng `@Transactional` bao bọc Service gọi nhiều Application Services, vì tất cả chung một Database Monolith.
R
Xử lý giao dịch nhanh gọn, an toàn mà không cần đến pattern phức tạp như Saga hay Outbox.
#8 Tại sao hệ thống không dùng kiến trúc 3 lớp (3-tier) truyền thống? ▼
S
Kiến trúc 3 lớp (Controller-Service-Repository) thường dẫn đến Anemic Domain Model (Logic dồn hết vào Service, Model chỉ có getter/setter).
T
Cần đưa logic nghiệp vụ y tế phức tạp vào chính các thực thể (Entities) để dễ quản lý.
A
Áp dụng Clean/Hexagonal Architecture: Đưa logic vào Domain Model, Service chỉ làm nhiệm vụ điều phối.
R
Logic y tế được gom về một mối, dễ viết Unit Test, chống lại sự phình to của God Classes (Service hàng ngàn dòng code).
#9 Ứng dụng CQRS có được xem xét trong dự án không? ▼
S
Màn hình Dashboard của bác sĩ cần hiển thị dữ liệu tổng hợp từ rất nhiều bảng khác nhau.
T
Tách biệt luồng Ghi (Command) phức tạp khỏi luồng Đọc (Query) đòi hỏi tốc độ cao.
A
Áp dụng CQRS mức độ nhẹ: Các API báo cáo/thống kê truy vấn thẳng bằng native SQL thay vì đi qua Domain Repository.
R
Tối ưu tốc độ load dashboard lên gấp 5 lần mà không phá vỡ tính đóng gói của luồng ghi dữ liệu.
#10 Bạn quản lý sự phụ thuộc (Dependencies) của các module ra sao? ▼
S
Trong Monolith, các developer rất dễ 'tiện tay' import class của module khác vào dùng trực tiếp.
T
Cần cơ chế tự động ngăn chặn việc vi phạm ranh giới kiến trúc.
A
Sử dụng thư viện ArchUnit trong bước Unit Test để kiểm tra quy tắc import package (vd: `billing` không được import `appointment`).
R
Kiến trúc được bảo vệ liên tục trên CI/CD, không ai có thể vô tình phá vỡ ranh giới module.

🔐 Bảo mật & Tuân thủ y tế (PHI Compliance)

#11 Hệ thống tuân thủ bảo mật y tế (PHI) bằng cách nào? ▼
S
Thông tin sức khỏe cá nhân (PHI) nếu bị rò rỉ sẽ vi phạm pháp luật và phá hủy danh tiếng bệnh viện.
T
Mã hóa toàn bộ dữ liệu nhạy cảm (tên, CCCD, bệnh án) ngay cả khi DBA truy cập database trực tiếp.
A
Áp dụng AES-GCM (chuẩn mã hóa quân đội) ở tầng Application trước khi lưu xuống PostgreSQL.
R
Dữ liệu ở Database luôn ở dạng mã hóa. Dù hacker dump được database cũng không đọc được thông tin bệnh nhân.
#12 Tại sao lại dùng thuật toán AES-GCM? ▼
S
Có rất nhiều thuật toán mã hóa đối xứng, cần chọn thuật toán vừa bảo mật vừa có hiệu năng tốt.
T
Bảo mật dữ liệu nhưng không được làm chậm quá trình hiển thị hồ sơ của bác sĩ.
A
Chọn AES với chế độ GCM (Galois/Counter Mode) vì có hỗ trợ phần cứng (AES-NI) và cung cấp tính toàn vẹn dữ liệu (AEAD).
R
Tốc độ mã hóa/giải mã cực nhanh (micro-seconds) và chống lại việc hacker sửa đổi bản mã (tampering).
#13 Làm sao tìm kiếm (Search) bệnh nhân khi dữ liệu đã mã hóa? ▼
S
Dữ liệu tên và CCCD đã bị mã hóa thành chuỗi ngẫu nhiên, không thể dùng lệnh `LIKE` hay `WHERE` trong SQL.
T
Cần tìm kiếm chính xác bệnh nhân theo CCCD hoặc Tên một cách cực kỳ nhanh.
A
Sử dụng kỹ thuật Hashed Indexing: Tạo thêm một cột lưu giá trị băm (SHA-256) của chuỗi tìm kiếm (đã salt).
R
Truy vấn Database qua cột Hash với index B-Tree tốc độ cao (O(log n)), bảo mật mà vẫn giải quyết bài toán tìm kiếm.
#14 Quản lý Key Mã hóa (Encryption Keys) như thế nào? ▼
S
Nếu lưu Key mã hóa dạng plaintext trong file `.env` hoặc source code, hacker đọc được file sẽ giải mã được toàn bộ DB.
T
Cần một cơ chế an toàn để tiêm (inject) Key vào ứng dụng khi chạy.
A
Sử dụng môi trường biến bảo mật trên CI/CD, hoặc Vault. Key không bao giờ được hardcode.
R
Đảm bảo tính an toàn tuyệt đối cho Master Key. Có chiến lược Key Rotation để thay đổi key định kỳ.
#15 RBAC (Role-Based Access Control) hoạt động thế nào? ▼
S
Bệnh viện có nhiều chức danh (Bác sĩ, Lễ tân, Kế toán) với giới hạn quyền rất phức tạp.
T
Cấp quyền đúng người đúng việc, chặn đứng nỗ lực truy cập trái phép leo thang đặc quyền.
A
Triển khai hệ thống RBAC với 7 Roles và 36 Permissions chi tiết. Bọc API bằng `@PreAuthorize('hasAuthority("...")')`.
R
Kiểm soát an ninh tuyệt đối ở mức Method. Lễ tân không thể gọi API xem bệnh án chi tiết.
#16 Bảo vệ API khỏi brute-force attacks như thế nào? ▼
S
Hacker có thể chạy script dò mật khẩu liên tục vào endpoint `/api/v1/auth/login`.
T
Ngăn chặn bot spam nhưng không khóa nhầm tài khoản của người dùng hợp lệ.
A
Cài đặt cơ chế Rate Limiting (Token Bucket) ở API Gateway (Spring Security) cho các endpoint nhạy cảm.
R
Hạn chế tối đa 5 request/giây cho API login. Tự động block IP nếu vượt ngưỡng.
#17 Bạn xử lý Audit Logging (Nhật ký kiểm toán) ra sao? ▼
S
Trong y tế, cần phải biết chính xác 'Ai đã xem hồ sơ của ai vào lúc nào'.
T
Lưu lại vết (trail) của mọi hành động thay đổi dữ liệu và xem dữ liệu nhạy cảm.
A
Sử dụng Spring Data JPA `@EntityListeners` và Interceptor để tự động ghi log mọi thao tác CRUD kèm theo UserID.
R
Có đầy đủ lịch sử kiểm toán phục vụ thanh tra, phát hiện sớm các bác sĩ có dấu hiệu tra cứu hồ sơ sai quy định.
#18 Nếu lộ JWT Access Token, rủi ro là gì và chống thế nào? ▼
S
Token có thể bị đánh cắp qua mã độc trên máy tính hoặc bắt gói tin.
T
Giảm thiểu 'bán kính sát thương' (blast radius) khi token rơi vào tay kẻ xấu.
A
Đặt thời gian sống (TTL) của Access Token rất ngắn (15 phút).
R
Hacker dù lấy được token cũng chỉ dùng được tối đa 15 phút. Sau đó token tự chết.
#19 Refresh Token được bảo mật như thế nào? ▼
S
Refresh Token có tuổi thọ dài (7 ngày), nếu hacker lấy được sẽ tạo được vô hạn Access Token.
T
Bảo vệ Refresh Token hoàn toàn khỏi các cuộc tấn công XSS từ client.
A
Backend trả về Refresh Token dưới dạng `httpOnly`, `Secure` Cookie. JavaScript của frontend hoàn toàn không đọc được.
R
Triệt tiêu hoàn toàn rủi ro bị đánh cắp token bằng XSS script. An toàn tuyệt đối ở trình duyệt.
#20 Chống tấn công CSRF bằng cách nào khi dùng Cookie? ▼
S
Vì dùng Cookie cho Refresh Token, hệ thống dễ bị tấn công giả mạo yêu cầu (CSRF).
T
Đảm bảo trình duyệt chỉ gửi cookie khi request xuất phát từ chính domain của bệnh viện.
A
Set thuộc tính `SameSite=Strict` cho Cookie và thiết lập cơ chế CORS (Cross-Origin Resource Sharing) chặt chẽ trên Spring Boot.
R
Ngăn chặn 100% các cuộc tấn công CSRF từ các trang web lừa đảo thứ ba.

🔄 Xử lý đồng thời & Giao dịch (Concurrency)

#21 Vấn đề Double-booking (đặt trùng lịch) giải quyết thế nào? ▼
S
Hai bệnh nhân cùng lúc bấm nút đặt khám cùng một bác sĩ vào đúng cùng một khung giờ.
T
Chỉ cho phép duy nhất 1 người đặt thành công, người kia phải nhận thông báo 'Lịch đã đầy'.
A
Sử dụng Optimistic Locking với cột `@Version` trong bảng DB. Người thứ 2 lưu lại sẽ bị `OptimisticLockException`.
R
Tránh việc lock toàn bộ bảng làm chậm hệ thống (như Pessimistic Locking), hiệu năng cao mà data luôn chuẩn xác.
#22 Trạng thái phòng khám (Queue) được quản lý ra sao? ▼
S
Bệnh nhân có các trạng thái phức tạp: Đã Check-in, Đang Khám, Hoàn Thành, Hủy bỏ.
T
Ngăn chặn các thao tác sai quy trình (ví dụ: đang 'Đợi khám' nhảy thẳng sang 'Hoàn thành').
A
Thiết kế một State Machine (Máy trạng thái) trong lớp Domain Service để quy định luồng chuyển đổi trạng thái hợp lệ.
R
Workflow y tế được thực thi nghiêm ngặt, mọi nỗ lực chuyển trạng thái trái phép đều bị từ chối kèm lỗi rõ ràng.
#23 Pessimistic Locking được áp dụng khi nào? ▼
S
Khi module Pharmacy (Nhà thuốc) thực hiện thao tác trừ tồn kho (Inventory) lúc bán thuốc.
T
Tránh tình trạng Race Condition bán quá số lượng thuốc thực tế có trong kho.
A
Dùng `@Lock(LockModeType.PESSIMISTIC_WRITE)` trên query tìm thuốc để khóa row trong database cho đến khi transaction kết thúc.
R
Đảm bảo tồn kho chính xác tuyệt đối 100% trong môi trường thanh toán đồng thời cao.
#24 Xử lý Transaction thất bại giữa chừng như thế nào? ▼
S
Đang tạo hóa đơn thanh toán thì bị lỗi mạng rớt database.
T
Đảm bảo dữ liệu không bị lưu nửa vời (tạo lịch xong nhưng chưa tạo hóa đơn).
A
Tận dụng thuộc tính ACID của PostgreSQL thông qua Spring `@Transactional(rollbackFor = Exception.class)`.
R
Hệ thống tự động Rollback toàn bộ thay đổi. Database luôn ở trạng thái nhất quán.
#25 Mức độ cô lập (Isolation Level) của DB là gì? ▼
S
Cần cấu hình Isolation Level để tránh các hiện tượng như Dirty Read hay Phantom Read.
T
Đảm bảo dữ liệu hiển thị cho bác sĩ luôn là dữ liệu đã được chốt (committed).
A
Sử dụng mức mặc định của PostgreSQL là `Read Committed`, kết hợp khoá ứng dụng khi cần thiết.
R
Hiệu năng database được tối ưu tối đa mà không gặp rủi ro đọc dữ liệu sai lệch.
#26 Làm sao chặn người dùng bấm nút Submit nhiều lần? ▼
S
Người dùng sốt ruột bấm nút 'Đặt lịch' 5 lần liên tục.
T
Ngăn backend nhận và xử lý 5 request giống hệt nhau sinh ra data rác.
A
Ở Frontend (React), disable nút sau khi click. Ở Backend, dùng Idempotency Key (chặn request tạo mới nếu đã có).
R
Loại bỏ hoàn toàn lỗi duplicate data do thói quen thao tác của người dùng.
#27 Bạn xử lý Deadlock trong Database như thế nào? ▼
S
Nhiều transaction cập nhật chéo các bảng (A->B và B->A) dẫn đến khóa chết lẫn nhau.
T
Phát hiện, gỡ rối và phòng ngừa deadlock để hệ thống không bị treo.
A
Sắp xếp thứ tự cập nhật các bảng luôn theo một chiều cố định. Bắt exception và retry transaction (cơ chế Backoff).
R
Hệ thống không bao giờ bị đứng, tự động phục hồi khỏi các va chạm dữ liệu hiếm hoi.
#28 Tối ưu hóa các tiến trình chạy ngầm (Background Jobs)? ▼
S
Việc gửi email nhắc lịch khám cho 10.000 bệnh nhân ngày mai mất quá nhiều thời gian.
T
Chạy background job mà không làm nghẽn luồng xử lý API chính của ứng dụng.
A
Sử dụng Spring `@Async` và Thread Pool để đẩy tác vụ gửi mail ra luồng phụ, hoặc dùng Spring Batch.
R
Bệnh nhân nhận email đúng giờ, API chính của hệ thống không bị ảnh hưởng hiệu năng.
#29 Tại sao hệ thống không dùng Message Queue (Kafka/RabbitMQ)? ▼
S
Quy mô hệ thống 1 bệnh viện chưa tới mức xử lý hàng triệu sự kiện mỗi giây.
T
Giữ hệ thống đơn giản, giảm chi phí vận hành (Ops) nhưng vẫn hiệu quả.
A
Dùng Spring Application Events cho giao tiếp bất đồng bộ nội bộ hệ thống.
R
Tiết kiệm chi phí bảo trì server MQ, đáp ứng thừa sức lưu lượng nội bộ bệnh viện.
#30 Làm gì khi có lỗi trong tiến trình bất đồng bộ? ▼
S
Sự kiện 'Bệnh nhân thanh toán thành công' gửi đi nhưng module 'Gửi hóa đơn email' bị lỗi.
T
Đảm bảo email sẽ được gửi lại mà không làm ảnh hưởng giao dịch thanh toán chính.
A
Lưu sự kiện vào bảng Outbox trong database. Có một cron job định kỳ quét và gửi lại các email báo lỗi.
R
Đạt được tính nhất quán cuối cùng (Eventual Consistency) mà không làm mất dữ liệu sự kiện.

☕ Spring Boot 3.3 & Java 17 Core

#31 Tại sao dự án chọn Java 17 thay vì Java 11? ▼
S

#64 Chống tấn công XSS khi hiển thị Ghi chú y tế của Bác sĩ? ▼
S
Bác sĩ có thể copy-paste dữ liệu từ web khác chứa mã độc JavaScript ngầm vào form.
T
Khi hiển thị ghi chú cho người khác xem, phải đảm bảo mã độc không được thực thi.
A
React tự động escape mọi text nội dung. Với các đoạn cần hiển thị Rich Text, dùng thư viện `DOMPurify` để khử trùng nội dung HTML.
R
Triệt tiêu rủi ro Hacker khai thác XSS (Cross-Site Scripting) để đánh cắp token của người dùng khác.
#65 Debounce tính năng Tìm kiếm bệnh nhân như thế nào? ▼
S
Khi lễ tân gõ tên 'Nguyễn Văn A', nếu mỗi ký tự gõ ra gọi API 1 lần sẽ làm chết server.
T
Giảm thiểu lượng API call mà vẫn có gợi ý tìm kiếm realtime.
A
Sử dụng custom hook `useDebounce` để trì hoãn việc gọi API 500ms sau khi người dùng ngừng gõ phím.
R
Giảm 90% lượng request lên server, trải nghiệm gõ phím của lễ tân cực mượt.
#66 Tối ưu danh sách dài (Hàng ngàn bệnh nhân) không bị giật lag? ▼
S
Trình duyệt sẽ bị treo (freeze) nếu phải render thẻ HTML của 5000 bệnh nhân cùng lúc.
T
Hiển thị danh sách siêu dài cuộn mượt mà với 60 FPS.
A
Áp dụng kỹ thuật Virtualization (Cửa sổ ảo) sử dụng thư viện `tanstack/react-virtual`.
R
Dù danh sách có 1 triệu dòng, DOM chỉ chứa đúng 20 dòng đang hiển thị trên màn hình. Tốc độ cuộn mượt hoàn hảo.
#67 Cách hiển thị thông báo (Toast/Snackbar) không chặn luồng thao tác? ▼
S
Người dùng lưu thành công hồ sơ, cần báo hiệu rõ ràng nhưng không bắt họ phải bấm 'OK' để tắt bảng thông báo (alert).
T
Thiết kế thông báo nổi thân thiện với UX.
A
Sử dụng thư viện `react-hot-toast` hoặc `sonner` để gọi Toast từ bất kỳ đâu trong code.
R
Thông báo trượt đẹp mắt, tự biến mất sau 3 giây, cải thiện độ chuyên nghiệp của phần mềm.
#68 Bạn tổ chức cấu trúc Component trong React như thế nào? ▼
S
Nếu vứt mọi component vào chung một thư mục `components`, dự án sẽ sớm trở thành bãi rác khó tìm kiếm.
T
Áp dụng cấu trúc thư mục quy chuẩn, dễ mở rộng.
A
Thiết kế theo mô hình Atomic Design hoặc Feature-based (gom components, hooks, api theo tính năng như `/features/appointments`).
R
Team dễ dàng tìm file, các tính năng đóng gói thành các module Frontend độc lập tương tự như Backend.
#69 Làm sao để UI thân thiện với thiết bị di động (Responsive)? ▼
S
Bác sĩ không chỉ dùng máy tính bàn mà còn dùng iPad khi đi buồng bệnh.
T
Giao diện phải tự động co giãn đẹp trên mọi kích thước màn hình.
A
Sử dụng hệ thống lưới CSS Grid/Flexbox và các class tiện ích của TailwindCSS (ví dụ: `md:grid-cols-2`).

Code CSS nằm ngay trong thẻ HTML tiện lợi, 1 source code phục vụ mượt mà trên cả PC lẫn Tablet.
#70 Bạn ứng xử với tình trạng mạng yếu (Offline/Slow Network) thế nào? ▼

T
Không để người dùng bị 'đứng màn hình' mà không hiểu chuyện gì xảy ra.

🔑 Authentication & Authorization (JWT, RBAC)

#71 Quy trình đăng nhập (Login flow) diễn ra thế nào? ▼
S
Cần một cơ chế cấp phát chứng chỉ an toàn khi user cung cấp đúng email/password.
T
Tạo luồng bảo mật tiêu chuẩn để nhận diện user.
A
Backend xác thực password (BCrypt), sinh ra `AccessToken` (dạng JSON) và `RefreshToken` (đính kèm vào httpOnly Cookie).
R
User truy cập được hệ thống, AccessToken được lưu tạm trên RAM (Zustand state) của trình duyệt để gắn vào Header `Authorization`.
#72 Tại sao không lưu Access Token vào LocalStorage? ▼
S
LocalStorage rất tiện, nhưng có thể bị JavaScript đọc được thông qua hàm `localStorage.getItem`.
T
Bảo vệ token khỏi mọi nỗ lực trộm cắp bằng mã độc XSS.
A
Chỉ lưu `AccessToken` trong bộ nhớ RAM của ứng dụng React (Zustand/Context). Sẽ mất khi F5 tải lại trang.
R
An toàn tối đa. Tuy F5 sẽ bị mất state, nhưng hệ thống sẽ dùng `RefreshToken` (từ Cookie) để tự động lấy lại AccessToken mới trong im lặng.
#73 Luồng Silent Refresh (Cấp lại token ngầm) hoạt động ra sao? ▼
S
AccessToken chỉ sống 15 phút. Không thể bắt bác sĩ cứ 15 phút lại gõ mật khẩu lại.
T
Duy trì phiên đăng nhập vô hình mà vẫn đảm bảo tính ngắn hạn của AccessToken.
A
Dùng Axios Interceptors ở Frontend. Khi gọi API báo lỗi 401 (Hết hạn), Interceptor tự động tạm dừng request, gọi API `/refresh-token`, lấy Token mới rồi tiếp tục request cũ.
R
Trải nghiệm mượt mà, bác sĩ không hề biết token đã hết hạn và được cấp lại ngầm.
#74 Làm sao để 'Đăng xuất' (Logout) an toàn tuyệt đối? ▼
S
Người dùng dùng xong máy tính chung của bệnh viện muốn thoát.
T
Đảm bảo tài khoản không bị xài lén sau khi đã đứng lên.
A
Frontend xóa AccessToken trên RAM. Gọi API Backend `/logout` để Backend xóa httpOnly Cookie của Refresh Token.
R
Hủy diệt hoàn toàn phiên đăng nhập trên cả 2 đầu Client và Server, an toàn tuyệt đối.
#75 Backend verify JWT Token như thế nào? ▼
S
Backend nhận được chuỗi JWT từ Frontend. Phải biết đây là token xịn hay giả mạo.
T
Xác minh tính xác thực và thời hạn mà không cần gọi vào Database.
A
Sử dụng Thư viện JJWT để dùng Secret Key (hoặc Public Key thuật toán RSA) giải mã kiểm tra chữ ký (Signature) của token.
R
Quá trình kiểm tra diễn ra trong vài phần nghìn giây hoàn toàn trong bộ nhớ CPU, hệ thống chạy siêu nhanh.
#76 Bạn xử lý phân quyền 36 chức năng trên Frontend thế nào? ▼
S
Menu bên trái có chức năng 'Quản lý doanh thu' chỉ dành cho Kế toán. Nếu Bác sĩ login thì không được thấy.
T
Ẩn/hiện giao diện thông minh dựa vào phân quyền.
A
Payload của JWT Token chứa danh sách các `permissions` (ví dụ: `['READ_PATIENT', 'CREATE_PRESCRIPTION']`). Custom component `` sẽ bọc các nút chức năng lại.
R
Giao diện sạch sẽ, chỉ hiển thị những tính năng user có quyền sử dụng, tránh việc bấm vào nút rồi mới nhận thông báo lỗi 403.
#77 Password được lưu trong Database bằng thuật toán gì? ▼
S
Quy định cấm lưu mật khẩu nguyên bản (plaintext) hoặc mã hóa băm yếu (như MD5/SHA1).
T
Làm cho hacker dù ăn trộm được database cũng mất hàng trăm năm để dò ngược ra mật khẩu.
A
Sử dụng `BCrypt` với cấu hình độ khó (Work Factor / Strength) là 12.
R
An toàn tuyệt đối. Mật khẩu 123456 cũng sinh ra chuỗi mã hóa khác nhau ở mỗi user do tính năng tự động sinh Salt của BCrypt.
#78 Nếu một Role cần thay đổi Quyền (Permission) ngay lập tức? ▼
S
Admin vừa quyết định tước quyền 'Xóa bệnh án' của Role Bác sĩ.
T
Cập nhật phải có hiệu lực ngay mà không bắt toàn bộ bác sĩ phải đăng nhập lại.
A
Thiết kế JWT không chứa trực tiếp mảng Permissions, mà chỉ chứa UserID. Spring Security sẽ cache quyền trong Redis và load lại khi Role thay đổi.
R
Hệ thống linh hoạt, áp dụng thay đổi đặc quyền theo thời gian thực (Real-time).
#79 Chống Brute-force mật khẩu (Thử mật khẩu liên tục)? ▼
S
Kẻ tấn công dùng tool tự động thử hàng ngàn mật khẩu vào một tài khoản Lễ tân.
T
Chặn đứng nỗ lực dò mật khẩu.
A
Thêm cơ chế đếm số lần đăng nhập sai. Sai 5 lần liên tiếp sẽ khóa tài khoản (Account Locked) trong 30 phút. Hoặc áp dụng CAPTCHA.
R
Bảo vệ hệ thống khỏi các nỗ lực tấn công tự động (Bots).
#80 CORS (Cross-Origin Resource Sharing) trong kiến trúc này? ▼
S
Frontend chạy ở `hms-app.com`, Backend chạy ở `api.hms-app.com`. Trình duyệt mặc định sẽ chặn gọi chéo domain.
T
Bật cấu hình an toàn để Frontend gọi được API mà không bị chặn.
A
Cấu hình Spring Boot `@CrossOrigin` hoặc WebMvcConfigurer chỉ cho phép domain `hms-app.com` được gọi với các method GET, POST, PUT, DELETE.
R
Chặn các trang web lừa đảo gọi API của bệnh viện ngầm, trình duyệt là lá chắn bảo vệ hoàn hảo.

🧪 Testing & Đảm bảo chất lượng (QA)

#81 Mục tiêu Test Coverage của dự án là bao nhiêu? ▼
S
Cần một con số để định lượng chất lượng code, tránh việc code lỗi lên Production.
T
Yêu cầu 100% code nghiệp vụ (Domain Layer) phải có test.
A
Sử dụng JaCoCo (Java) để đo coverage. Thiết lập quy tắc trên CI/CD: Nếu Coverage dưới 80% thì đánh rớt bản Build (Build Fails).
R
Mọi thay đổi code đều được bao bọc bởi màng lưới an toàn, chống lại sự suy thoái tính năng (Regression).
#82 Unit Test cho Domain Layer trong Spring Boot? ▼
S
Lớp Domain chứa logic tính giá tiền hóa đơn bệnh viện. Cần test độc lập.
T
Viết test chạy cực nhanh, không phụ thuộc Framework hay Database.
A
Sử dụng JUnit 5. Khởi tạo trực tiếp class bằng lệnh `new` và truyền dữ liệu ảo vào hàm tính toán, dùng `assertEquals` kiểm tra.
R
Test chạy xong trong vài mili-giây, là minh chứng cho việc thiết kế kiến trúc Clean Architecture rất dễ test.
#83 Bạn dùng Mockito vào việc gì? ▼
S
Lớp Application Service cần gọi hàm `save()` của Database, nhưng trong Unit Test không bật Database.
T
Giả lập các hành vi ngoại vi để test phần logic cốt lõi bên trong Service.
A
Dùng `@Mock` để tạo phiên bản giả của Repository, `@InjectMocks` để tiêm vào Service. Dùng `when().thenReturn()` để định nghĩa câu trả lời giả.
R
Lập trình viên kiểm soát được toàn bộ kịch bản nhánh (thành công, văng lỗi) mà không cần setup Database thật phức tạp.
#84 Tại sao dùng Testcontainers cho Integration Test? ▼
S
Dùng DB ảo in-memory như H2 dễ gây lỗi cú pháp SQL khác biệt với PostgreSQL thật khi deploy lên Prod.
T
Cần môi trường test giống hệt 100% môi trường Production.
A
Thư viện Testcontainers sẽ tự động quay (spin-up) một container Docker chạy PostgreSQL thật ngay khi chạy Integration Test.
R
Bắt được những lỗi đặc thù của Postgres (như pgvector, JSONB) ngay ở local, tăng độ tin cậy tuyệt đối cho code.
#85 Playwright dùng để làm gì trong khâu Testing? ▼
S
Mọi logic Back/Front đều tốt, nhưng ghép lại màn hình chạy thực tế thì ấn nút không ăn.
T
Kiểm thử luồng thao tác như một người dùng thật trên trình duyệt thực.
A
Viết kịch bản E2E Test bằng Playwright. Bot tự động mở Chrome, điền form đăng nhập, click đặt lịch và kiểm tra thông báo màn hình.
R
Kiểm tra toàn vẹn luồng chảy hệ thống (End-to-End). Đảm bảo các luồng (Happy Path) quan trọng nhất không bao giờ hỏng.
#86 Xử lý bài toán 'Test Flaky' (Test chập chờn lúc xanh lúc đỏ)? ▼
S
Trong E2E test, thỉnh thoảng test bị fail do mạng chậm làm nút bấm chưa kịp hiện ra.
T
Làm cho test E2E trở nên ổn định, có tính lặp lại (Deterministic).
A
Thay vì dùng hàm chờ cố định tĩnh `sleep(5000)`, Playwright dùng cơ chế `auto-wait` chờ đúng thẻ DOM xuất hiện hoặc mạng rảnh rỗi mới click.
R
Test ổn định 99.9%, không bị gián đoạn CI pipeline vì những lỗi timing ngớ ngẩn.
#87 SonarQube Quality Gate bắt được những lỗi gì? ▼
S
Review code bằng mắt người thường bỏ sót các lỗi tiềm ẩn (Code Smell, Security Hotspots).
T
Tự động hóa việc soát lỗi mã nguồn tĩnh (Static Code Analysis).
A
Cấu hình SonarQube phân tích code mỗi lần Push. Phát hiện mật khẩu hardcode, biến không dùng, vòng lặp vô hạn.
R
Duy trì mã nguồn đạt chuẩn hạng A (A-grade rating). Loại bỏ nợ kỹ thuật (Technical Debt) ngay từ lúc sơ khai.
#88 Bạn kiểm thử cơ chế bảo mật (AES-GCM) như thế nào? ▼
S
Cần chứng minh chức năng mã hóa dữ liệu hoạt động hiệu quả.
T
Bảo đảm hàm lưu DB gọi hàm mã hóa, hàm lấy ra gọi hàm giải mã.
A
Viết Integration test: Lưu một Bệnh nhân vào DB qua Service, sau đó dùng `JdbcTemplate` đọc thẳng DB bằng native query để Assert (khẳng định) dữ liệu đọc ra không giống tên gốc.
R
Bằng chứng bằng code khẳng định 100% PHI data đã bị mã hóa ở mức vật lý.
#89 Test hiệu năng (Load Testing) bằng công cụ gì? ▼
S
Ban Giám đốc hỏi: Hệ thống chịu được bao nhiêu bác sĩ thao tác cùng lúc?
T
Tìm ra giới hạn chịu đựng (Bottlenecks) của máy chủ.
A
Sử dụng công cụ K6 hoặc JMeter. Viết kịch bản giả lập 500 người dùng liên tục gọi API đặt lịch khám trong 5 phút.
R
Biết trước hệ thống sẽ đuối ở mức CPU hay RAM, để lên kế hoạch tăng cấu hình server (Scale up) trước khi triển khai.
#90 Khái niệm TDD (Test-Driven Development) có áp dụng không? ▼
S
Dự án yêu cầu chất lượng cao, thường code xong mới viết test rất lười và hay viết chống đối.
T
Thay đổi tư duy: Viết Test trước, viết Code sau.
A
Bắt đầu bằng việc viết 1 test fail cho logic 'Không được đặt lịch ở quá khứ'. Sau đó code logic if-else để test đó Pass màu xanh.
R
Code sinh ra luôn luôn khớp với yêu cầu nghiệp vụ, không có một dòng code thừa (YAGNI).

🚀 DevOps, CI/CD & System Design

#91 Docker mang lại lợi ích gì cho team Dev HMS? ▼
S
Trước kia bạn A cài Java 17, Postgres 15, bạn B xài Java 11, Postgres 14 sinh ra lỗi 'Works on my machine'.
T
Đồng nhất tuyệt đối môi trường chạy app từ máy Dev đến máy Production.
A
Đóng gói Spring Boot và Next.js thành các Docker Images bằng Dockerfile. Khởi chạy toàn bộ hệ thống bằng `docker-compose up`.
R
Bất kỳ ai join team mới chỉ cần 1 lệnh duy nhất là hệ thống chạy hoàn hảo trong 2 phút, không rắc rối cài đặt.
#92 Tối ưu Dockerfile cho Spring Boot thế nào? ▼
S
Nếu copy toàn bộ file `.jar` nặng 100MB vào Docker, mỗi lần sửa 1 dòng code build lại phải push cục 100MB lên mạng.
T
Tối ưu hóa thời gian build và dung lượng ảnh (Image Size).
A
Sử dụng Layered Jar và Multi-stage build. Tách các thư viện (Dependencies ít thay đổi) và Code (thường xuyên thay đổi) thành các Layer riêng biệt.
R
Chỉ có layer chứa Code (vài Kilobytes) bị build lại. Thời gian deploy rút ngắn từ 2 phút xuống còn 10 giây.
#93 Mô tả quy trình CI/CD Pipeline bằng GitHub Actions? ▼
S
Triển khai code thủ công qua FTP hoặc SSH dễ gây lỗi downtime và không đồng bộ.
T
Tự động hóa hoàn toàn luồng Đưa code lên mạng -> Cài đặt.
A
Tạo workflow `.github/workflows/main.yml`. Trình tự: Checkout Code -> Build Java/Node -> Chạy Test -> Build Docker -> Push sang Registry -> Bắn lệnh update cho Server.
R
Mỗi lần Merge vào nhánh `main`, hệ thống tự động kiểm tra và lên Prod sau 3 phút mà không cần can thiệp của con người.
#94 Làm sao để hệ thống cập nhật bản mới không bị gián đoạn (Zero Downtime)? ▼
S
Nếu tắt Server cũ để bật Server mới, bệnh viện sẽ bị mất kết nối 30 giây.
T
Nâng cấp hệ thống trong khi bác sĩ đang thao tác mà không bị rớt mạng.
A
