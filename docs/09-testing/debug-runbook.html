Phương pháp debug

Hệ thống này có 5 tầng phụ thuộc. Một lỗi ở tầng trên hầu như luôn là triệu chứng của tầng dưới. Đừng debug màn hình trắng ở frontend khi backend chưa boot — bạn sẽ mất hàng giờ cho một biến môi trường bị thiếu.

M-1

M-2

Đọc envelope API — mọi response đều cùng một hình dạng

Mọi endpoint trả về đúng cấu trúc này (ApiResponse.java). Nhìn success và error.code là biết ngay lỗi thuộc tầng nào — không cần đoán.

Thành công 
{
  "success": true,
  "data": { ... },
  "message": "Request completed successfully",
  "error": null,
  "pagination": null,
  "timestamp": "2026-07-27T..."
}
Thất bại 
{
  "success": false,
  "data": null,
  "message": "...",
  "error": {
    "code": "FORBIDDEN",
    "message": "..."
  },
  "timestamp": "..."
}
Dấu hiệu bất thường Nếu response không có envelope này (ví dụ trang lỗi Whitelabel dạng HTML, hoặc JSON trần), nghĩa là request chưa vào tới controller — nó bị chặn ở filter (Security / RateLimit) hoặc sai URL. Đây là manh mối rất mạnh.

04

Xác thực & vòng đời token

Hai cổng đăng nhập tách biệt: /api/v1/auth cho nhân viên, /api/v1/patient-auth cho bệnh nhân. Access token trả trong body; refresh token đặt trong cookie httpOnly — bạn sẽ không thấy nó trong JS, và đó là chủ ý.

4.1

Đăng nhập nhân viên và lấy token

curl -i -X POST http://localhost:8081/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"doctor1@hospital.vn","password":"Doctor@1234"}'
Kỳ vọng — kiểm tra cả hai Body: data.accessToken có giá trị, data.refreshToken là null (đã được làm sạch có chủ đích).
Header: có Set-Cookie chứa refresh token kèm cờ HttpOnly.
Đọc đúng ý nghĩa refreshToken: null trong body không phải lỗi. Server cố tình chỉ gửi refresh token qua cookie httpOnly để JavaScript không đọc được (chống XSS).
4.2

Gọi endpoint cần xác thực

# Dán access token lấy từ bước 4.1
$T = "<access_token>"
curl http://localhost:8081/api/v1/me -H "Authorization: Bearer $T"
MãÝ nghĩaHướng điều tra
200Token hợp lệSang Phase 05
401Token sai / hết hạn / thiếu tiền tố BearerKiểm tra tiền tố và khoảng trắng; token có bị cắt khi copy không
403Token hợp lệ nhưng thiếu quyềnKhông phải lỗi auth — sang Phase 05
Phân biệt 401 và 403 — rất quan trọng 401 = “tôi không biết bạn là ai” (vấn đề token). 403 = “tôi biết bạn, nhưng bạn không được phép” (vấn đề role). Nhầm hai mã này là nguyên nhân debug sai hướng phổ biến nhất.

Mẫu test đối chứng — chiều dương và chiều âm

Một endpoint chỉ được coi là đã kiểm thử khi bạn xác nhận cả hai chiều: đúng vai trò thì vào được, sai vai trò thì bị chặn. Chỉ test chiều dương sẽ bỏ lọt lỗ hổng phân quyền.

# Hàm tiện dụng — PowerShell
function Login($email, $pass) {
  $r = curl -s -X POST http://localhost:8081/api/v1/auth/login `
    -H "Content-Type: application/json" `
    -d "{`"email`":`"$email`",`"password`":`"$pass`"}" | ConvertFrom-Json
  return $r.data.accessToken
}

$doc = Login "doctor1@hospital.vn" "Doctor@1234"
$acc = Login "accountant@hospital.vn" "Acc@1234"

# Chiều dương: kế toán đọc hoá đơn → mong đợi 200
curl -s -o /dev/null -w "accountant to invoices : %{http_code}`n" `
  http://localhost:8081/api/v1/invoices -H "Authorization: Bearer $acc"

# Chiều âm: bác sĩ đọc hoá đơn → mong đợi 403
curl -s -o /dev/null -w "doctor to invoices     : %{http_code}`n" `
  http://localhost:8081/api/v1/invoices -H "Authorization: Bearer $doc"
Kỳ vọng Kế toán nhận 200, bác sĩ nhận 403. Nếu bác sĩ nhận 200 → Lỗ hổng phân quyền.
6.3

Kiểm tra bảo vệ dữ liệu bệnh nhân (BOLA)

Bảo mật

Lỗi BOLA (truy cập đối tượng của người khác) là rủi ro lớn nhất trong hệ thống y tế. Đăng nhập bằng một bệnh nhân, rồi thử đọc dữ liệu của bệnh nhân khác bằng cách đổi ID trên URL.

# Đăng nhập bệnh nhân A, rồi thử truy cập hồ sơ của bệnh nhân B
curl -i http://localhost:8081/api/v1/patient-portal/records/<ID_CUA_B> \
  -H "Authorization: Bearer <TOKEN_CUA_A>"
Kỳ vọng 403 hoặc 404 — tuyệt đối không được trả dữ liệu của B. Nếu trả 200 kèm dữ liệu → dừng test, đây là lỗi nghiêm trọng nhất có thể có.
Bối cảnh của repo này Dự án từng có một lỗi BOLA đã được vá (PR #35, nhánh fix/bola-clinical-access). Đây là vùng đáng kiểm tra kỹ mỗi khi sửa code liên quan tới truy cập hồ sơ lâm sàng.

Quản trị (admin)

  • /admin/audit-logs ghi nhận các thao tác trên

  • Xem kết quả xét nghiệm khi bác sĩ đã trả

  • Thử đổi ID trên URL → phải bị chặn (xem 6.3)

Bộ test tự động

Khi test thủ công tìm ra bug, hãy dùng test tự động để khoanh vùng. Lưu ý quan trọng: phần lớn E2E specs không chạy trong CI và cần backend thật.

9.1

Backend — chạy từ hẹp tới rộng

cd backend
mvn test -pl application      # 122 test tầng service — nhanh nhất
mvn test -pl controller       # 58 test controller
mvn test -pl infrastructure   # 30 test repository
mvn verify                    # ~183 test tích hợp (Testcontainers — cần Docker)
Chiến lược Chạy -pl application trước: nhanh, không cần Docker, bắt phần lớn lỗi logic. Chỉ chạy mvn verify khi nghi ngờ lỗi ở tầng tích hợp thật (SQL, transaction, security filter). Ngưỡng JaCoCo: instruction ≥ 40%, branch ≥ 30%.
9.2

Frontend

cd frontend
npm run test:unit            # 641 test / 70 file — không cần backend
npm run lint
npm run build                # bắt lỗi type & build phía server

npm run test:e2e:ci          # 12 specs, chạy bằng mock — giống CI
npm run test:e2e:ui          # 21 specs @ui — chỉ chạy local
npm run test:e2e:integrated  # cần backend thật đang chạy
npm run test:e2e:headed      # mở trình duyệt để nhìn tận mắt
npm run test:e2e:report      # xem báo cáo sau khi chạy
Đừng hiểu nhầm phạm vi test Trong 2.045 test E2E, chỉ 930 chạy ở CI gate và chúng dùng mock — nghĩa là chúng kiểm tra route guard phía frontend, không kiểm tra phân quyền phía server. Phân quyền thật được bảo đảm bởi mvn verify. Đặt HMS_REQUIRE_BACKEND=true để các spec cần backend báo lỗi rõ ràng thay vì âm thầm tự bỏ qua.
